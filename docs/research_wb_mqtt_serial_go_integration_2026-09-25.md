# Исследование: более нативная интеграция Go с wb-mqtt-serial для WB-MR6C v.3

Этап 1 · 25 сентября 2026 года · контекст: [дорожная карта](roadmap_evse_line_control_go_2026-09-25.md), разделы 2, 4, 5, 7.

Исследован исходный код [wb-mqtt-serial](https://github.com/wirenboard/wb-mqtt-serial) на коммите `832fb9d` от 24.09.2026, шаблон `templates/config-wb-mr6cv3.json.jinja`, библиотека [wbgong](https://github.com/wirenboard/wbgong) и APT-репозиторий Wiren Board. На стенде ничего не проверялось: пометка «проверить» означает, что вывод сделан по коду и документации.

## 1. Вывод

Здесь «более нативная» интеграция означает, что Go получает синхронный ответ «записано / не записано», а не публикует сообщение без обратной связи. Для этого не нужен cgo. У драйвера есть штатный MQTT-RPC: `device/Set` и `device/Load` работают по схеме «запрос — ответ» и выполняются в цикле опроса порта с высоким приоритетом.

| Вариант | Оценка | Когда выбирать |
|---|---|---|
| **A.** Топики `/devices/.../controls/K1/on` | Годится для демо, для ядра слаб | Только для отображения и отладки |
| **B.** MQTT-RPC `device/Set` / `device/Load` + подписка на состояние | **Рекомендуется для MVP** | Штатный драйвер, синхронное подтверждение записи |
| **C.** cgo поверх ядра wb-mqtt-serial | Не рекомендуется | Только если встраивание в один процесс обязательно |
| **D.** Нативный Modbus RTU-over-TCP на Go | Серьёзная альтернатива B | Если нужно, чтобы таймаут опроса MR6C служил watchdog'ом Go-цикла |

Главная новая находка касается раздела 5 дорожной карты. Выбор между B и D определяется не задержкой, а тем, кто является мастером шины. Встроенный безопасный режим MR6C срабатывает только при отсутствии Modbus-пакетов. Пока шину опрашивает wb-mqtt-serial, зависание Go этот режим не включит. В варианте D единственным мастером становится Go, и тот же таймер начинает контролировать работоспособность нашего цикла управления. Это не заменяет независимую аварийную цепь, но становится второй линией защиты без дополнительного оборудования.

Предлагаемый порядок: реализовать адаптер B, параллельно сделать прототип адаптера D за тем же контрактом `SetOutput / ReadSnapshot / Watch` и сравнить их на стенде (раздел 7).

> **Обновление после уточнения топологии (раздел 9).** Система — это 100+ постов, на каждом свой WB-MGE v.3, один счётчик Меркурий 234 ART-01PR и не меньше одного WB-MR6C. Рекомендация меняется на **гибрид D + B**. MR6C опрашивает напрямую Go по Modbus TCP, отдельно на каждом шлюзе, и таймаут опроса модуля становится watchdog'ом цикла управления для своего поста. Счётчики опрашивает wb-mqtt-serial через прозрачный мост на втором порту шлюза. cgo по-прежнему не нужен.

## 2. Как устроен драйвер (что важно для интеграции)

```text
main.cpp
 ├─ TMosquittoMqttClient ─ libwbmqtt TDriver (MQTT backend, retained, libwbmqtt.db)
 │    └─ TMQTTSerialDriver ─ TSerialPortDriver (по потоку на порт)  ← MQTT-адаптер
 │                              └─ TSerialClient                      ← ядро опроса
 │                                   ├─ TSerialDevice / TModbusDevice
 │                                   ├─ регистры, планировщик опроса, Fast Modbus события
 │                                   └─ TFeaturePort (serial / tcp)
 └─ TMqttRpcServer ─ RPC-обработчики (port/*, device/*, config/*, fw-update/*)
                      └─ ISerialClientTask → очередь задач того же TSerialClient
```

- **Граница есть, но она внутренняя.** `TSerialClient` ([serial_client.h](https://github.com/wirenboard/wb-mqtt-serial/blob/master/src/serial_client.h)) не знает о MQTT: `AddDevice`, `Cycle`, `SetTextValue`, колбэки чтения и ошибки, `AddTask`. MQTT подключается в `TSerialPortDriver`: `WBMQTT::PControl`, `PDriverTx`.
- **libwbmqtt используется повсюду.** Её заголовки подключают 67 файлов `src/`, включая JSON, логирование, парсинг конфигурации и шаблонов. Даже без MQTT библиотеку придётся собирать и линковать.
- **Сборка.** Makefile собирает все `.cpp`, кроме `main.cpp`, в `COMMON_OBJS`, из которых собираются бинарник и тесты. Статическую библиотеку из них получить легко, а стабильного C++ API у неё нет. C++20, `-Werror`, зависимости: libwbmqtt1-5 (≥ 5.6), libcurl, gurux (DLMS) в `thirdparty`.
- **Лицензия** MIT-WB, производная от MIT: форк и встраивание разрешены. Проверить формулировку перед поставкой.
- **Пакеты для Pi 5.** В `deb.wirenboard.com` сборка arm64 есть только для `wb8/bullseye`: wb-mqtt-serial 2.248.1, libwbmqtt1-5 5.6.0, зависимость от `libssl1.1` и `wb-utils`. Для bookworm стабильных пакетов arm64 нет. На Raspberry Pi OS bookworm драйвер и libwbmqtt придётся собирать из исходников, как и предусматривает этап 1. Это касается вариантов A, B и C; для D не нужно.

## 3. Вариант B — MQTT-RPC вместо топиков `/on`

Топик запроса: `/rpc/v1/wb-mqtt-serial/<сервис>/<метод>/<client_id>`, ответ приходит в тот же топик с суффиксом `/reply` (JSON-RPC: `id`, `result`, `error{code,message,data}`).

| Метод | Назначение в нашем ПО | Что показал код |
|---|---|---|
| `device/Set` `{"device_id":"wb-mr6cv3_<addr>","channels":{"K1":1}}` | `SetOutput` | `RPCDeviceSetTask` вызывает `Device->WriteSetupRegisters(port, …)` синхронно в потоке порта. `error: null` означает, что устройство подтвердило Modbus-запись. Ошибка порта даёт `-32000`, таймаут — `-32600` |
| `device/Load` `{"device_id":…,"channels":["K1","Real State K1","Input 1"]}` | `ReadSnapshot`, контрольное чтение после записи и после reconnect | Читает устройство. Кэш, описанный в README, относится к `device/LoadConfig` (настройки), а не к каналам. Проверить на стенде |
| `device/LoadConfig` / `device/Set` c `parameters` | Проверка и установка безопасных настроек MR6C при старте | Для `LoadConfig` есть кэш, нужен `"force": true` |
| `device/SetPoll` | Не использовать для управления | Опрос возобновляется автоматически через 10 минут |
| `ports/List` | Диагностика конфигурации | — |

Что это даёт по сравнению с `/on`:

1. **Подтверждение на уровне команды.** Запись в `/on` асинхронная: результат виден только косвенно через `meta/error` (флаг `w`) и смену значения. RPC возвращает результат конкретной операции. Это закрывает правила 3–4 раздела 3 дорожной карты: таймаут RPC означает «исход неизвестен», дальше выполняется `device/Load` и сверка.
2. **Нет retained-команд.** RPC-запрос не retained, у ответа есть `id`. Риск «запоздалой ON после reconnect» (раздел 4) переходит к библиотеке MQTT-клиента в Go: отключить автоматическую повторную отправку QoS1 после переподключения либо публиковать RPC с QoS 0 и повторять только после сверки.
3. **Свежее чтение без ожидания цикла опроса**: `device/Load` отправляется в шину сразу после текущего цикла.

Ограничения:

- В README сказано, что RPC рассчитан на разовые операции, а не на постоянный опрос. Поток изменений по-прежнему берём из подписки на `/devices/wb-mr6cv3_N/controls/+` и `…/meta/error`, а RPC используем для команд и контрольных чтений.
- Нужно проверить, обновляет ли `device/Set` опубликованное значение контрола сразу или только после следующего чтения/события. Для логики это неважно: подтверждение даёт ответ RPC плюс `device/Load`.
- В wb-mqtt-serial нет своей авторизации. Доступ к `/rpc/v1/wb-mqtt-serial/#` на запись ограничиваем ACL брокера (раздел 4).
- Готового Go-клиента для WB MQTT-RPC нет. Протокол простой: около 100 строк поверх `github.com/eclipse/paho.golang` или `paho.mqtt.golang`.

## 4. Вариант C — cgo

Код подтверждает оценку раздела 7 дорожной карты и уточняет её:

- Минимальная граница для C ABI — `TSerialClient` и `TSerialDevice`, загружаемые из шаблонов через `TTemplateMap` и `serial_config`. `TSerialPortDriver`, libwbmqtt `TDriver` и RPC-сервер из сборки исключаются. Вместо них нужен свой слой около 300–600 строк C++: колбэки регистров → очередь событий, `SetTextValue` → команда, `AddTask` → синхронные чтения. Без ответа от `TSerialClient` синхронного «записано» нет: подтверждение придётся собирать из колбэка ошибки или своей `ISerialClientTask`, то есть повторить логику `RPCDeviceSetTask`.
- libwbmqtt всё равно нужна в сборке, но только как утилитарная библиотека (JSON, лог, потоки), без MQTT-клиента.
- Своя сборка C++20 под bookworm/arm64, отслеживание внутренних классов, у которых нет обязательств совместимости, общий процесс с Go (падение C++ завершает приложение).
- Выигрыш: отсутствие брокера и одного IPC-перехода, то есть порядка миллисекунд на локальной машине. Это пренебрежимо рядом с RS-485 на 9600–115200 бод, шлюзом и механикой контактора (десятки миллисекунд).

**Итог:** C ABI оправдан только требованием «один процесс, без брокера». Если B или D это требование закрывают, от ветки 7 можно отказаться, а сэкономленные 3–5 дней потратить на D.

## 5. Вариант D — нативный Modbus на Go

### Карта регистров WB-MR6C v.3 (из шаблона, адреса с 0)

| Назначение | Тип | Адрес | Примечание |
|---|---|---|---|
| Выход K1…K6 | coil | 0…5 | Запись FC05 — идемпотентная «установить ON/OFF» |
| Фактическое состояние K1…K6 | discrete | 96…101 | Прошивка ≥ 1.24.0; в шаблоне `enabled: false`, при варианте B включить в конфиге |
| Вход 1…6 / вход 0 | discrete | 0…5 / 7 | 7 входов, «сухой контакт» |
| Команды Off / On / Toggle K | coil | 100+ / 108+ / 116+ | Не использовать toggle |
| Режим входа | holding | 9…14, 16 | Отвязка входов от выходов: матрица 384+ |
| Безопасное состояние выхода | holding | 930…935 | 0 = Off |
| Действие в безопасном режиме | holding | 938…943 | 1 = «перевести в безопасное состояние» |
| Управление входами в безопасном режиме | holding | 946…951 | 1 = запретить |
| Источник безопасного режима | holding | 19 | 0 = таймаут опроса или питание шины, 2 = только таймаут |
| Таймаут опроса, с | holding | 8 | 1…65534, по умолчанию 10 |
| Задержки при включении / перезапуске | holding | 1728+ / 1744+, 1752+ | Минимальная пауза между включениями реализуется и в модуле |

Библиотеки Go с поддержкой RTU-over-TCP для прозрачного шлюза: [simonvetter/modbus](https://github.com/simonvetter/modbus) (MIT, `rtuovertcp://`, обновлялась в июле 2026) и [grid-x/modbus](https://github.com/grid-x/modbus) (BSD-3, сентябрь 2026). Для режима Modbus TCP подходят обе.

### Плюсы

- **Таймаут опроса модуля становится watchdog'ом нашего цикла.** Контрольное чтение и запись выполняет сам цикл управления, а не отдельная goroutine (иначе нарушено требование раздела 5). Если цикл завис, пакеты прекращаются, и через `poll_timeout_s` MR6C переводит выходы в OFF. Модуль сам не восстанавливает ON, если не настроено «восстановление после выхода из безопасного режима». Настроить и проверить.
- Прямой контроль над таймаутами, повторами и признаком «исход неизвестен» без двух промежуточных очередей (MQTT и драйвер).
- Нет C++-сборки и брокера на Pi 5. Одна статически собранная Go-программа.

### Минусы

- **Один мастер на шину.** wb-mqtt-serial и Go не могут одновременно опрашивать одну линию RS-485 через один шлюз: кадры RTU от двух клиентов перемешаются. Нужно либо убрать этот порт из конфигурации wb-mqtt-serial, либо выделить MR6C отдельную линию. Как WB-MGE ведёт себя при нескольких TCP-клиентах, проверить.
- Свой опрос, backoff и переподключение, а также своя карта регистров. Её можно генерировать из шаблона WB и сверять с ним в тестах, чтобы не расходиться с прошивками.
- Нет Fast Modbus событий «из коробки»: опрашиваем discrete 0…7 и 96…101 одним-двумя запросами с периодом 50–200 мс. Для 14 бит это дёшево.
- Теряем homeui и wb-rules для этого модуля. Для контура безопасности это скорее плюс, для обслуживания минус. Прошивку обновлять штатными средствами при остановленном Go.

Встроенный безопасный режим MR6C — функция прошивки того же модуля, что управляет катушками. Поэтому он **не является** независимой аварийной цепью из раздела 5 и не отменяет её.

## 6. Отброшено

- **wbgong.** Это только интерфейсы. Реализация загружается через `plugin.Open("wbgo.so")`, то есть Go-плагин из экосистемы контроллеров WB. Go-плагины требуют совпадения версии тулчейна и зависимостей, а готового `.so` для Raspberry Pi 5 нет. Практической пользы для проекта нет.
- **`device/SetPoll` как watchdog.** Пауза опроса автоматически снимается через 10 минут и повторно выполняет setup-секцию. Для контура безопасности семантика неподходящая.

## 7. Предлагаемый стендовый эксперимент (2–3 дня, внутри этапа 1)

Цель: выбрать между B и D по измерениям, а не по предположениям.

1. Собрать libwbmqtt и wb-mqtt-serial на Pi 5 (bookworm, arm64). Зафиксировать коммиты и скрипт сборки.
2. Адаптер B: `SetOutput` = `device/Set` → `device/Load(K, Real State K)`. Адаптер D: FC05 → FC02 (96+) → FC01. Оба реализуют один Go-интерфейс.
3. Для каждого варианта снять 1000 циклов ON/OFF: время до ответа записи, время до подтверждения фактического состояния, время до смены НЗ-входа, p50/p99.
4. Сценарии отказов: `kill -STOP` Go-процесса (B: выходы остаются, D: OFF через `poll_timeout_s`), остановка брокера или драйвера, разрыв LAN и RS-485, таймаут записи с последующей сверкой.
5. Для D: поведение WB-MGE при втором TCP-клиенте; восстановление после безопасного режима без самопроизвольного ON.
6. Решение фиксируется записью (ADR) в дорожной карте.

- Нужны ли на этом шлюзе другие устройства под wb-mqtt-serial (счётчики, homeui)? Если да, вариант D требует отдельной линии RS-485.

## 9. Пересмотр с учётом топологии: 100+ постов, на каждом свой WB-MGE v.3

Уточнение пользователя: более 100 шлюзов WB-MGE v.3, к каждому подключены один счётчик Меркурий 234 ART-01PR (5–60 А, 230/400 В) и не меньше одного WB-MR6C. Дальше это называется «пост».

Масштаб отличается от раздела 1 дорожной карты: там один шлюз, 3×1Ф + 1×3Ф, около 22 кВт. Раздел 1, лимиты ввода и оценки сроков нужно пересмотреть отдельно.

### 9.1. Что даёт шлюз ([документация WB-MGE v.3](https://wiki.wirenboard.com/wiki/WB-MGE_v.3_Modbus_Ethernet_Gateway))

- Два порта RS-485, **режим задаётся отдельно для каждого порта**. TCP-порты по умолчанию: 502 → RS485-1, 503 → RS485-2. Скорость 1200–115 200 бит/с.
- **Modbus TCP**: шлюз сам преобразует Modbus TCP ↔ RTU, до 8 TCP-клиентов на порт.
- **Прозрачный мост**: протокол любой, **только один мастер на порт**.
- Fast Modbus через шлюз работает в обоих режимах. В wb-mqtt-serial он включён для TCP-портов с RTU (прозрачный мост) всегда, для `modbus_tcp` — только с `connected_to_mge: true` ([`feature_port.cpp`](https://github.com/wirenboard/wb-mqtt-serial/blob/937284d82ccd5d616b5664b7febc566b3e7ca2de/src/port/feature_port.cpp)). При одном-двух модулях на шине он не нужен.
- «Кэширующий мультимастер» и сниффер — надстройки над режимами. Для порта MR6C их нужно выключить, см. 9.3.

Раскладка по портам на каждом посту:

| Порт | Устройства | Режим MGE | Кто мастер | Скорость |
|---|---|---|---|---|
| RS485-1 (TCP 502) | WB-MR6C ×1…N | Modbus TCP | **только Go** | 115 200 |
| RS485-2 (TCP 503) | Меркурий 234 ART-01PR | Прозрачный мост | wb-mqtt-serial (`port_type: "tcp"`, `protocol: "mercury230"`) | По паспорту счётчика, по умолчанию 9600 |

Протокол Меркурий — не Modbus, поэтому второй порт может работать только прозрачным мостом. Разнесение по портам исключает конфликт протоколов и двух мастеров на одной шине.

### 9.2. Почему теперь D для MR6C

Раньше вариант D ограничивали две вещи: опрашивать сотню модулей на одной шине самим и терять Fast Modbus. При одном-двух модулях на шину обе проблемы исчезают:

- **Бюджет шины тривиальный.** Одна транзакция при 115 200 бит/с через шлюз — порядка 4–6 мс. Для одного MR6C хватает трёх запросов: FC02 по входам 0…7, FC02 по фактическому состоянию выходов 96…101, FC01 по выходам 0…5. Это около 15–20 мс, так что период опроса 100 мс даёт большой запас. Оценка, проверить на стенде.
- **Отказ изолирован по постам.** У каждого поста своя goroutine, своё TCP-соединение, свой автомат переподключения. Недоступность или зависание одного шлюза не влияет на остальные.
- **Таймаут опроса MR6C становится watchdog'ом Go-цикла для своего поста.** Кроме Go, в шину этого порта никто не пишет. Если Go перестаёт общаться с модулем, через `poll_timeout_s` MR6C переводит выходы в безопасное состояние OFF. Это то, что раздел 5 дорожной карты требовал от внешнего устройства. Без выделенного модуля разрешения, предложенного в прошлой версии, теперь можно обойтись.
- **Не нужен cgo и C++ для контура управления.** wb-mqtt-serial остаётся только для счётчиков, то есть вне контура безопасности.

Условие корректности watchdog'а. Раздел 5 запрещает heartbeat из отдельной goroutine при зависшей логике. Поэтому трафик к MR6C разрешается **арендой (lease)**, которую продлевает цикл управления:

```text
controller tick (для поста p):
    проверить правила, обработать наблюдения, обновить автомат состояний
    lease[p] = now + leaseTTL            // продлевает только цикл управления

adapter goroutine поста p:
    loop:
        if now > lease[p]: прекратить ЛЮБОЙ обмен с MR6C (ни чтений, ни записей), ждать
        иначе: опрос / выполнение команд
```

Если цикл завис, аренда истекает, адаптер замолкает и MR6C отключает выходы. Если завис сам адаптер, трафик тоже прекращается, и результат тот же. `leaseTTL` должен быть меньше `poll_timeout_s`, а у `poll_timeout_s` минимум 1 с и шаг в целые секунды. Время срабатывания: `leaseTTL + poll_timeout_s + время отпускания реле и контактора`. Численное значение согласовать на этапе 0.

### 9.3. Обязательные настройки и проверки MR6C

Адреса регистров — из раздела 5. Go при подключении читает эти настройки (FC03) и **не разрешает включение** поста, если они отличаются от эталона. Это защита от дрейфа конфигурации, например после замены модуля.

| Настройка | Регистр | Значение |
|---|---|---|
| Источник безопасного режима | 19 | 2 (таймаут опроса) или 0 (таймаут или питание шины) — выбрать на этапе 0 |
| Таймаут опроса, с | 8 | согласованное значение |
| Безопасное состояние выходов | 930…935 | 0 (Off) |
| Действие в безопасном режиме | 938…943 | 1 (перевести в безопасное состояние) |
| Управление входами в безопасном режиме | 946…951 | 1 (запретить) |
| Состояние при подаче питания | по шаблону | «безопасное состояние» |
| Связь входов с выходами (матрица) | 384+ и режимы входов | отключена: НЗ-входы не должны управлять катушками |

Проверить на стенде:

- Модуль не восстанавливает ON сам после выхода из безопасного режима. Если восстанавливает — отключить эту настройку.
- Шлюз в режимах Modbus TCP, кэша и сниффера **сам не посылает** Modbus-пакетов модулю. Иначе таймер будет сбрасываться без участия Go. Проверить анализатором шины.
- Второй TCP-клиент на порту 502 сбрасывает таймер модуля. Поэтому доступ к порту 502 закрыть сетевыми правилами, оставив только Go-хост. Сервисные работы (обновление прошивки, homeui) — отдельная процедура с выведенным из работы постом.

Встроенный безопасный режим — прошивка того же модуля, что управляет катушками. Он не покрывает, например, сваривание контакта реле внутри MR6C. Независимая аварийная цепь из раздела 5 дорожной карты по-прежнему нужна.

### 9.4. Счётчики через wb-mqtt-serial

- В `/etc/wb-mqtt-serial.conf` — 100+ портов `tcp` (IP шлюза, 503), на каждом один счётчик. Драйвер ведёт отдельный поток на порт, поэтому посты независимы и по счётчикам. Нагрузку (100+ потоков и сокетов, переподключения недоступных шлюзов) проверить на Pi 5. Ожидается, что она невелика.
- Конфиг вручную не поддерживается. Нужен генератор из реестра постов (IP, адреса, типы). Задать явный `id` устройства, например `post017_meter`, чтобы MQTT-топики однозначно соответствовали посту. Генератор добавить в этап 4 дорожной карты.
- Go читает показания подпиской на `/devices/post017_meter/controls/+` и `…/meta/error`. RPC для счётчиков не нужен.
- При одном счётчике на шину цикл из 5–7 каналов займёт порядка 0,3–0,5 с (оценка). Каждый канал — отдельный запрос, минимальный таймаут 150 мс. Этого хватает для контроля фазных токов поста. Приоритеты задаются через `read_period_ms`: токи и мощности по фазам часто, энергия по тарифам редко.
- Протокол: шаблон `config-mercury234.json` в репозитории — для **234 D** (DLMS) и нам не подходит. Исполнение ART, по сведениям производителя, работает по протоколу Меркурий 230. Проверить по паспорту и прошивке, при необходимости сделать свой шаблон на базе `mercury230`. Адрес счётчика, скорость и пароль доступа взять в реестр постов.
- Позже, если захочется убрать wb-mqtt-serial целиком, протокол Меркурий 230/234 можно реализовать на Go: описание обмена публикует производитель. Для MVP не нужно: счётчики вне контура безопасности.
- Отсутствие тока по счётчику не доказывает отключения линии (раздел 1 дорожной карты). Счётчик — источник `measurement`, а не обратная связь контактора.

### 9.5. Скорректированная архитектура

```text
Raspberry Pi 5
  Go-приложение
    API → правила/бюджет фаз по вводу → автоматы состояний постов (lease на каждый пост)
       ├─ hardware/mr6c: по goroutine и TCP-соединению на пост → WB-MGE[i]:502 (Modbus TCP)
       └─ measurements/wbmqtt: подписка MQTT ← wb-mqtt-serial ← WB-MGE[i]:503 (прозрачный мост)
  локальный брокер MQTT (ACL), wb-mqtt-serial (сгенерированный конфиг, только счётчики)

Изолированная сеть/VLAN постов
  Пост i: WB-MGE v.3 ─ RS485-1 → WB-MR6C (1…N) → катушки контакторов, НЗ → входы MR6C
                     └ RS485-2 → Меркурий 234 ART-01PR
          + независимая аварийная цепь поста
```

Последствия масштаба для Go-части:

- **Массовые отказы.** Отказ Pi, коммутатора или сети — общий отказ: через `leaseTTL + poll_timeout_s` все посты уходят в OFF. Для безопасности это правильное поведение, но оно прерывает все зарядки сразу. Выбор значения таймаута — компромисс между безопасностью и доступностью, его нужно согласовать. Автоматического ON после восстановления нет (правило 6 раздела 3).
- **Шторм переподключений.** После восстановления сети 100+ постов переподключаются одновременно, поэтому backoff делать с джиттером. Сверку состояния выполнять по каждому посту отдельно.
- **Групповое «отключить всё»** выполняется параллельно по постам, это десятки миллисекунд, а не перебор. Аварийное отключение по-прежнему обеспечивает аппаратная цепь.
- **Реестр постов как источник конфигурации**: IP, адреса Modbus и счётчика, число MR6C, фазность, привязка к вводу. Одинаковые Modbus-адреса на разных шлюзах допустимы.
- **Бюджет мощности** теперь агрегирует 100+ постов по вводам и фазам. Это новая часть модели, в разделе 3 дорожной карты её нет.

### 9.6. Изменения к стендовому эксперименту (раздел 7)

1. Go ↔ WB-MGE (Modbus TCP, 502) ↔ MR6C: цикл ON/OFF, чтение фактического состояния и НЗ-входов, задержки p50/p99.
2. Watchdog: `kill -STOP` процесса Go, зависание цикла при живом адаптере, зависание адаптера, отключение кабеля Pi. Во всех случаях выходы OFF за `leaseTTL + poll_timeout_s`, без самопроизвольного ON после восстановления.
3. Анализатор шины RS485-1: трафик идёт только от Go, в том числе при включённых и выключенных функциях шлюза.
4. Меркурий 234 ART-01PR через прозрачный мост (503) с шаблоном `mercury230`: доступные параметры, время цикла, поведение при недоступном счётчике.
5. Масштаб без 100 шлюзов: Go против 100–200 симуляторов Modbus TCP (например, сервер из `simonvetter/modbus`), wb-mqtt-serial со 100+ портами `tcp` на недоступные адреса. Смотрим CPU, память, потоки, шторм переподключений.

Выбор B или D для MR6C этим экспериментом больше не решается. Он подтверждает гибрид и численные параметры.

### 9.8. Состав поста (уточнение пользователя)

На пост приходит трёхфазный ввод через счётчик. Дальше идут три однофазных контактора, каждый питает свою однофазную EVSE. Опционально есть трёхфазный контактор для трёхфазной EVSE. Одновременную работу трёхфазной EVSE и однофазных исключает программный режим блокировки. По сути это схема 3×1Ф / 1×3Ф из раздела 3 дорожной карты, повторённая на каждом посту.

**Допущение, требующее подтверждения:** K1 подключён к L1, K2 к L2, K3 к L3, то есть каждая однофазная EVSE на своей фазе.

#### Раскладка одного WB-MR6C

Одного MR6C на пост достаточно.

| Ресурс | Назначение | Примечание |
|---|---|---|
| K1, K2, K3 | Катушки однофазных контакторов EVSE-1…3 (L1…L3) | |
| K4 | Катушка трёхфазного контактора EVSE-3Ф | Только если на посту есть 3Ф |
| K5, K6 | Резерв | Не использовать под силовые функции без схемы |
| Вход 1…3 | НЗ-контакт K1…K3 (обратная связь) | Один НЗ на контактор |
| Вход 4 | НЗ-контакт трёхфазного контактора | |
| Вход 5…6, 0 | Резерв: состояние вводного автомата/УЗО, аварийной цепи поста, второй НЗ 3Ф | Позволяет отличить «отключено аварийной цепью» от неисправности |

Раздел 3 дорожной карты предполагал 8 входов (4 контактора × 2 НЗ). В этой схеме каждый контактор отдаёт **один НЗ на обратную связь**, а второй — на аппаратную блокировку (см. ниже). Хватает штатных 7 входов, расширение не требуется. Цена: ПО не видит состояние контакта, который участвует в блокировке. Отказ этого контакта обнаруживается только проверкой при обслуживании. Внести это в регламент.

#### Смысл блокировки 3×1Ф / 1×3Ф и что делать аппаратно

Одновременная работа режимов не даёт короткого замыкания: это разные нагрузки. Опасность в **перегрузке фаз ввода поста**. Счётчик 5–60 А, то есть не больше 60 А на фазу; реальный предел задают вводной автомат и кабель. Например, три однофазных EVSE по 32 А плюс трёхфазная 32 А дают до 64 А на каждой фазе. Поэтому блокировка — это прежде всего **ограничение нагрузки**, а не защита от межфазного замыкания.

- **Программная блокировка обязательна.** Это режим поста в конфигурации (`3x1`, `1x3`, `both` только при подтверждённом запасе по току), плюс последовательность переключения из раздела 3: отключить → подтвердить НЗ всех конфликтующих → пауза → включить.
- **Аппаратную блокировку рекомендуется добавить**, раз вторые НЗ всё равно свободны. Катушка 3Ф-контактора питается через последовательную цепь НЗ контакторов K1…K3. Общее питание катушек K1…K3 идёт через НЗ 3Ф-контактора. Тогда ни зависший Go, ни ошибочная запись в регистр не включат оба режима сразу. У исполнения 2НО+2НЗ всего два силовых полюса, поэтому для 3Ф нужен контактор на 3–4 НО с доп. блоком не меньше чем на 2 НЗ (замечание из раздела 3 в силе). Выбор аппаратов, изоляцию между цепью катушек (230 В) и цепью входов WB, а также защиту ввода определяет специалист по силовой части.
- Модульные контакторы разного типоразмера обычно нельзя механически сблокировать. Если нужна механическая блокировка, выбирать аппараты с учётом этого.
- Если блокировка чисто программная, её надёжность держится на ПО и на watchdog'е из 9.2. Итоговую защиту от перегрузки даёт вводной автомат. Это решение нужно явно зафиксировать на этапе 0.

#### Что даёт трёхфазный счётчик на посту

- **Бюджет по фазам поста.** В режиме `3x1` ток фазы Ln ≈ ток EVSE-n, если на вводе нет других нагрузок. В режиме `1x3` все три фазы — это одна EVSE. Резервировать по-прежнему нужно по максимальному согласованному току (раздел 3), а измерения использовать для контроля.
- **Диагностика по каждой линии.** Если контактор Kn в OFF подтверждён НЗ, а на фазе Ln стабильно есть ток выше порога, это авария: возможен сваренный НО-контакт, ошибка монтажа или посторонняя нагрузка. Пост блокируется. Обратное не работает: отсутствие тока не доказывает отключения (раздел 1). В режиме `both` или при других нагрузках на вводе проверка по фазе неоднозначна, её нужно отключать или адаптировать.
- **Контроль перегрузки.** Если ток по фазе приближается к лимиту ввода, это событие для оператора и запрет новых включений на посту. Цикл счётчика — порядка 0,3–0,5 с, это оценка. Этого мало для защиты, но достаточно для управления допуском.

#### Модель поста для Go

```text
Post {
  id, gateway_ip, mr6c_slave_id, meter{address, password_level}
  mode: 3x1 | 1x3 | both(с явным лимитом)       // программная блокировка
  lines: [
    {id: L1, output: K1, feedback: in1, phase: L1, evse: 1ф},
    {id: L2, output: K2, feedback: in2, phase: L2, evse: 1ф},
    {id: L3, output: K3, feedback: in3, phase: L3, evse: 1ф},
    {id: 3P, output: K4, feedback: in4, phase: L1+L2+L3, evse: 3ф, optional}
  ]
  groups: {single: [L1,L2,L3], three: [3P]}, conflicts: single↔three
  limits: {phase_max_a, evse_max_a[], min_off_time, mode_switch_pause}
  lease, safety_config_expected, input_config(отвязка входов от выходов)
}
```

Эталон настроек MR6C из 9.3 применяется ко всем четырём используемым выходам: безопасное состояние OFF, действие «перевести в безопасное состояние», управление входами в безопасном режиме запрещено. Входы 1…4 отвязаны от выходов, иначе НЗ «отпущенного» контактора может сам управлять катушкой. На K5, K6 то же самое, пусть они и не используются.

## 10. Меркурий 234 ART-01PR: пофазные данные для энергии сессии

Задача: определить, может ли счётчик отдать **накопленную энергию по каждой фазе** или только общий трёхфазный счётчик. Во втором случае энергия однофазной сессии рассчитывается из общего счётчика и мгновенных пофазных величин.

### 10.1. Что говорят источники

| Источник | Пофазная накопленная энергия | Мгновенные величины по фазам |
|---|---|---|
| [Каталог Инкотекс, 234 ART](https://www.incotexcom.ru/catalogue/234art) | Упомянут только учёт «по каждому тарифу», пофазно — **не указано** | Токи, напряжения, P/Q/S, cos φ по каждой фазе. Протоколы «Меркурий», СПОДЭС; RS-485 |
| [Руководство по эксплуатации Меркурий 234, ред. 2024, изм. 3 от 02.06.2026](https://doc.incotexcom.ru/hardware/234/) | Величины ALN+, ALN−, RLN± «для каждой фазы» описаны. Для каких исполнений и прошивок — **не ясно** | Мгновенные токи фаз и нейтрали, фазные и суммарные P, Q, S |
| [яЭнергетик, 234 ART](https://yaenergetik.ru/devices/mercury_234_art/) | Не указано | Мгновенные P, Q, токи, напряжения по фазам; RS-485 300–115 200 бит/с |
| Драйвер wb-mqtt-serial, шаблон `mercury230` | Каналы **AP1, AP2, AP3**: команда 0x05, массив 6 — пофазная A+, три значения **одним запросом** | P1–P3, Q1–Q3, U1–U3, I1–I3, PF1–PF3 (команда 0x08, параметр 0x11, **по запросу на каждую величину**) |

**Вывод:** протокол «Меркурий» предусматривает запрос пофазной энергии, и драйвер его реализует. Но поддержка у конкретного ART-01PR (год выпуска, версия прошивки) по документации **не подтверждается**. Мгновенные пофазные токи и мощности поддерживаются точно. Вопрос закрывается только проверкой на реальном счётчике.

### 10.2. Проверка на стенде (этап 1, полдня)

1. Прочитать через wb-mqtt-serial каналы `Total consumption` (A+ суммарно), `AP1`–`AP3`, `P1`–`P3`, `I1`–`I3`. Если AP недоступны, счётчик вернёт ошибку, и в MQTT у каналов появится `meta/error`.
2. Считать слово варианта исполнения и версию прошивки через `port/Load` сырым запросом по протоколу. Записать в реестр: по ним определяется поддержка пофазного учёта у партии счётчиков.
3. Нагрузить одну фазу известной нагрузкой на 1–2 часа. Проверить, что ΔAP1 ≈ ΔTotal, а ΔAP2 и ΔAP3 содержат только собственное потребление поста. Затем нагрузить три фазы разными токами и сравнить ΣΔAPn с ΔTotal.
4. Оценить дискретность: протокол отдаёт энергию в Вт·ч (в шаблоне `u32`, масштаб 0,001 кВт·ч), на индикаторе 0,01 кВт·ч. Проверить, с каким шагом реально меняются AP и Total.
5. Проверить чтение всех трёх фаз одной командой (0x08, параметры группы «по всем фазам»). В драйвере его нет, каждая величина — отдельный запрос. Если счётчик поддерживает групповое чтение, опрос P и I сокращается с 6 запросов до 2. Нужен собственный шаблон или, позже, реализация на Go. Номера параметров взять из протокола обмена производителя.

### 10.3. Расчёт энергии сессии

Общие правила:
- Снимок счётчика делается **до ON** (контактор подтверждённо OFF) и **после OFF** (подтверждено НЗ). Пока линия отключена, энергия по ней не растёт, поэтому задержка чтения счётчика не искажает результат.
- Каждое значение хранит источник, время и качество (`fresh` / `stale`). Сессия без обоих снимков получает качество `incomplete`.
- Собственное потребление БП поста на фазе питания вычитается как базовая линия либо фиксируется как известная погрешность. Оно незначительно, но на длинных сессиях накапливается.

**Вариант A — счётчик отдаёт пофазную энергию:**
- однофазная сессия на Ln: `E = ΔAPn`;
- трёхфазная сессия (`1x3`): `E = ΔTotal A+` (или `ΣΔAPn` с контролем расхождения).

Энергия по каждой линии берётся напрямую из счётчика, без расчёта.

**Вариант B — только общий счётчик:**
- **трёхфазная сессия** (`1x3`): `E = ΔTotal A+` — точно;
- **однофазная сессия, активна одна линия**: `E = ΔTotal A+` за время сессии за вычетом базовой линии БП;
- **однофазные сессии пересекаются во времени**: ΔTotal за каждый интервал между событиями ON/OFF распределяется пропорционально интегралу **пофазной активной мощности**:

```text
для интервала [t_i, t_{i+1}) между любыми событиями ON/OFF на посту:
    ΔE_i   = Total(t_{i+1}) − Total(t_i)            // по счётчику
    W_n,i  = ∫ P_n dt  (трапеции по опросам P1..P3)  // только для линий в ON
    E_n   += ΔE_i · W_n,i / Σ_k W_k,i
```

Почему P, а не I: ток не учитывает напряжение и коэффициент мощности, а пофазная активная мощность P1–P3 доступна со знаком. Ток I1–I3 используется для контроля лимита фаз и диагностики.

Свойства варианта B:
- Сумма распределённых энергий по построению равна показанию счётчика. Оценочным остаётся только разделение между фазами.
- Точность разделения зависит от периода опроса P (около 0,3–0,5 с, оценка) и пропусков. При разрыве опроса больше заданного предела интервал помечается `estimated`, интеграл по нему не экстраполируется.
- Для типичной зарядки с почти постоянным током ошибка разделения ожидаемо мала. Её нужно измерить на стенде (п. 3 в 10.2), а не заявлять.
- Снимки Total нужны на каждом событии ON/OFF поста, а не только в начале и конце сессии. Сразу после событий опрос Total делается внеочередным.

### 10.4. Ограничения и решения

- **Коммерческий учёт.** Разделённая расчётом энергия (вариант B) не является показанием поверенного средства измерения по линии. Если энергия сессии нужна для расчётов с пользователями, это **юридический** вопрос. Варианты: счётчик с подтверждённым пофазным учётом (вариант A), отдельный счётчик на каждую EVSE, данные поверенного счётчика EVSE. Расчёты с пользователями в первый выпуск не входят (раздел 1 дорожной карты), но выбор счётчика нужно сделать до закупки.
- **Снимки энергии связаны с событиями управления.** Контроллер после подтверждения ON/OFF запрашивает внеочередное чтение счётчика. Для этого подходит RPC `device/Load` wb-mqtt-serial по `device_id`: это разовая операция, а не постоянный опрос, что соответствует назначению RPC.
- **Хранение.** В журнал событий добавляются снимки энергии, интервалы и интегралы мощности, чтобы расчёт сессии можно было воспроизвести и проверить.
- **Опрос.** Каналы счётчика: P1–P3, I1–I3 с высоким приоритетом; Total A+ (массив, 1 запрос) и AP1–AP3 (1 запрос, если поддерживаются) — средний приоритет плюс внеочередное чтение на событиях; U, PF, тарифы — редко.

## 11. Энергия сессии для расчётов с пользователями

Решение пользователя от 25.09.2026: энергия сессии используется **для расчётов с пользователями**.

### 11.1. Следствия

- **Распределение по мощности (вариант B из 10.3) для расчётов непригодно.** Оно даёт оценку, а не показание средства измерения. Допустимо только как информационное значение и для контроля.
- **Каждая оплачиваемая сессия должна опираться на отдельный учётный регистр поверенного средства измерения.** Этот регистр за время сессии не должна менять другая нагрузка или другая сессия. Для однофазных EVSE это пофазный регистр, либо отдельный счётчик на линию.
- **Метрологию и юридическую модель нужно проверить с профильными специалистами.** Какие величины входят в метрологические характеристики по описанию типа средства измерения (ФГИС «Аршин»), требования к поверке и к ПО, передающему показания. Сюда же относится правовая форма продажи услуги зарядки. Это вне компетенции ПО; ниже — технические варианты.

### 11.2. Варианты

| Вариант | Состав поста | Оплачиваемая величина | Риски | Оценка |
|---|---|---|---|---|
| **R1. Счётчик на каждую EVSE** | Трёхфазный на вводе (лимиты, диагностика, трёхфазная сессия) + 3 однофазных после K1–K3 | Однофазная сессия — Δ однофазного счётчика линии. Трёхфазная — Δ A+ вводного, если собственные нужды поста запитаны **до** него, или отдельный трёхфазный после K4 | +3 счётчика на пост (×100+), место на DIN-рейке, 4–5 устройств на RS485-2 | **Рекомендуется**: не зависит от пофазного учёта, каждый регистр принадлежит одной линии |
| **R2. Один трёхфазный с пофазным учётом** | Как сейчас, но счётчик с подтверждённым пофазным учётом A+ | Однофазная — ΔALn+. Трёхфазная — ΔA+ | Нужно подтверждение, что пофазные регистры входят в метрологические характеристики типа. Собственные нужды поста в пофазном регистре. Текущий ART-01PR может не поддерживать | Дешевле, возможен после подтверждения метрологии |
| R3. Общий счётчик + распределение | Как сейчас | Расчётная | Не показание средства измерения | **Только для информации** |
| R4. Счётчик EVSE | Поверенный счётчик внутри EVSE | Регистр EVSE по OCPP или Modbus | Зависит от моделей EVSE; OCPP вне первого выпуска | Будущее расширение |

Для R1 и R2 собственные нужды поста (БП модулей) питать **до** учётных счётчиков или по отдельной цепи, чтобы пользователь не оплачивал их потребление. Уточнение к 9.9: БП подключается до контакторов **и до учётных счётчиков**. Как тогда учитывать собственное потребление, решает силовая часть.

**Однофазные счётчики, которые уже поддерживает wb-mqtt-serial** (шаблоны в репозитории): Меркурий 200 (`mercury200`, энергия с шагом 0,01 кВт·ч), Энергомера CE102/CE102M, НЕВА МТ 124, Милур 105/107S. Есть также универсальная поддержка DLMS/СПОДЭС (`protocol: "dlms"`). Критерии выбора модели:
- утверждённый тип и поверка;
- RS-485;
- протокол, поддерживаемый драйвером;
- дискретность регистра энергии не грубее 0,01 кВт·ч, лучше 1 Вт·ч;
- уникальный адрес на шине;
- журнал событий (вскрытие, пропадание питания);
- номинальный ток не ниже 32 А с запасом.

На RS485-2 можно разные протоколы на одной шине, но с контролем пересечения адресов и префиксов кадров (README драйвера, раздел о смешанных протоколах). Проще выбрать однофазные счётчики того же семейства и протокола.

### 11.3. Требования к ПО, чтобы данные годились для расчётов

1. **Источник — только показания регистра счётчика.** Энергия сессии = разность двух показаний одного регистра одного счётчика (серийный номер в записи). Никаких интегралов в оплачиваемой величине.
2. **Снимки привязаны к подтверждённым событиям.** Начальный снимок берётся, когда линия подтверждённо OFF, перед командой ON. Конечный — после подтверждённого OFF.
   - В R1 и R2 регистр линии при OFF не меняется, поэтому **допустимо позднее чтение**: если счётчик был недоступен в момент OFF, снимок берётся при восстановлении связи, до следующего ON этой линии.
   - Следствие для управления: **новое ON линии запрещено, пока не получен конечный снимок предыдущей сессии** и начальный новой.
3. **Качество сессии:**
   - `metered` — оба снимка получены, регистр принадлежит линии;
   - `incomplete` — нет снимка;
   - `disputed` — расхождение с контрольным расчётом выше порога, события счётчика (пропадание питания, вскрытие, смена времени), смена серийного номера.
   
   В расчёт с пользователем идут только `metered`. Остальные — по регламенту оператора.
4. **Контроль.** Контрольный расчёт по P (10.3) и по вводному счётчику сохраняется рядом как `estimated` для выявления неисправностей. Он никогда не подменяет показание.
5. **Неизменяемый журнал:**
   - снимки (значение, регистр, серийный номер счётчика, время по NTP и время счётчика, качество);
   - события линии и команды;
   - журналы событий счётчика.
   
   Только добавление записей, с контрольной суммой или цепочкой хешей записей. Резервное копирование вне Pi, срок хранения — по требованиям расчётов.
6. **Время.** Синхронизация Pi по NTP, контроль расхождения со временем счётчика. Тарифные зоны самого счётчика в расчёт сессии не вводить без решения по тарификации.
7. **Реестр** хранит серийные номера и дату поверки счётчиков каждой линии. Замена счётчика — событие, после которого сессии не склеиваются через разные серийные номера.
8. **Опрос учётных регистров:** внеочередное чтение по событиям ON/OFF (RPC `device/Load` по `device_id`) плюс периодическое для контроля; токи и мощности — как раньше, для лимитов и диагностики.

### 11.4. Что меняется в плане

- Этап 0: решение R1 или R2 с метрологом и юристом, выбор модели однофазного счётчика, схема питания собственных нужд до учётных счётчиков.
- Этап 1: проверка выбранного однофазного счётчика через wb-mqtt-serial на RS485-2 вместе с Меркурий 234; дискретность и позднее чтение.
- Этапы 2–3: модель сессии, снимки, блокировка ON до получения снимков, качество сессии, неизменяемый журнал. Оценка +3–5 рабочих дней.
- Обработка платежей и тарифы по-прежнему вне первого выпуска. Первый выпуск выдаёт **энергию сессии, пригодную для расчётов, с журналом-доказательством**.
